    Buffering

    128 buffers per client. If 129 is requested, return NO_MORE_CAPACITY.
    If 128 buffers are occupied, the server tells the client when 1 is freed. Send message RELEASED.
    Client will wait until it receives RELEASED to send more messages.

    Client messages that are not validated within 30 seconds will be erased.
    The client will be alerted with MESSAGE_ERROR.

    Each time a message has been parsed and verified to be complete, the server will send the client MESSAGE PROCESSED.
    The client will mark the earliest message sent with a processed state. Ideally later on with a message ID system.

    The entire buffer will be of x bytes.
    Each user will be given 65,536 bytes to occupy.
    This will be broken down to 128 segments.
    Each segments will be of 512 bytes.
    Each user will always have one buffer.

    The maximum size of a message is of 65,536 - header size (To be defined).

    One issue arises:
    For 1 Million Clients:
        65,536 * 1,048,576
        = 68,719,476,736 bytes
        = 64 GB in RAM.
        Which is not possible

    My VM of 4GB cannot handle this. But I will also not have 1 million clients.

    The size I can test with this setup is (using only 128 MB dedicated to message buffers):

    (0.125/64) * 100 = 0.001953125 * 100  = 0.1953125%

    So,
    1048576 * 0.001953125 = 2048 users

    Why request the entire memory space at the start rather than on user demand?
    Let's say we start with 10% of the max capacity.
    Eventually, this 10% has been occupied and the server allocates more.
    Now it is at 20% of max capacity.
    This repeats until reaching 60% of the max capacity.
    After this, the traffic decreses significantly, only 15% of the 60% available is in use.
    So some space should be freed.
    The problem is that the client buffers are dispersed among all of the buffer fragments.
    So the possible solutions are:
    1. Count occupancy of each buffer fragment and only freed once it is completely empty.
    - Will almost never happen.
    2. When a certain treshhold is reached, copy the least occupied fragment to other buffer fragments.
    - Resource intensive.
    Regardless of solution, the linked list that distributes buffer spaces for users will have to be constantly updated, by deleting, adding or reviewing.
    It will also complicate the easiness of distributing buffer space to users.
    Aditionally, why would it not occupy the total capacity? Will the RAM be occupied for other processes?
    If that's the case, those other processed could affect significantly the reliability of this server by decreasing the memory space arbitrarly.
    This is not the same as scaling the server, scaling is expected, but this would happen with additional instances of the server or a maintanance window to increase the total capacity.
    Allocating memory space on demand would only make sense in a cloud environment.

    This lead to my decision being to allocate all buffer space at the start of the program.
    * It ensures stability for the max allowed number of users.
    * Facilitates memory management.
